# Side-B 승인 설계 검증 리뷰

**전제**: 운영 환경변수, IAM, 트래픽·태그, 사용자 토큰, Google 로그인 E2E는 모두 미확인입니다. 아래에서 "현재 코드"는 환경변수 허용목록 구현을, "설계"는 미구현 문서를 가리킵니다.

## 1) 판정: 보완 후 가능

권한 분리 원칙은 이미 설계에 있습니다. 서버 UID 관리자 목록, Firestore 클라이언트 거부, DB 장애 시 503, legacy 제거, 미리듣기 승인 검사, revision·감사 트랜잭션이 해당합니다. 따라서 에뮬레이터 기반 구현은 바로 착수할 수 있습니다. 다만 운영 전환은 아래 P1을 해결한 뒤에 해야 합니다.

## 2) 남은 위험

**[P1] 구 리비전 태그 URL로 승인·차단 우회**
- **위치**: docs:109, extension/auth.config.js:10, apiConfig.js:13-14·28, auth.py:219-223·250-260
- **근거**:
  - 설계 109줄은 확장 기본 주소를 "날짜 태그 URL"이라고 적었습니다. 그러나 현재 기본값은 일반 서비스 URL입니다(apiConfig.js:1-2). 태그 URL은 v2 이관 대상일 뿐입니다.
  - Cloud Run 태그는 트래픽 0%여도 해당 리비전을 계속 서비스하는 것으로 알고 있습니다(이 환경에서는 미확인).
- **시나리오**: 차단된 사용자나 공유 토큰 보유자가 curl로 `auth-20260915-...` 태그를 직접 호출합니다. 그러면 dual 모드와 환경변수 허용목록이 그대로 적용되어 기능이 실행됩니다. 이 우회는 확장 수정과 무관하게 서버 측에서 발생합니다.
- **보완**:
  - 전환 전에 구 정책 리비전의 태그를 모두 제거합니다.
  - auth.config.js:10에서 태그 origin을 제거합니다.
  - 109줄의 전제를 현재 코드에 맞게 정정합니다.
- **인수 테스트**: `gcloud run services describe`로 태그 목록을 확인합니다. 구 태그 URL이 404 또는 신 정책으로 응답하는지 확인합니다. 차단 계정이 모든 공개 URL에서 403을 받는지 확인합니다.

**[P2] 경로·작업 ID 형식 미규정**
- **위치**: docs:88, docs:76-78
- **시나리오**: `{uid}`나 `operation_id`에 `/`가 들어가면 Firestore 경로가 하위 컬렉션 문서로 해석될 수 있습니다.
- **보완**:
  - UID는 1~128자이고 `/`를 금지하는 정규식으로 검증합니다.
  - operation_id는 UUID 형식으로 제한합니다.
  - 감사 키를 `admin_uid:operation_id`로 구성합니다.
- **인수 테스트**: `a/b`, 빈 값, 129자 입력은 422를 반환해야 합니다.

**[P2] 요청 제한이 인스턴스 로컬이고 /auth/me는 제한이 없음**
- **위치**: auth.py:270, routers/auth.py:18-58(consume 호출 없음), docs:93(신청·목록만 제한)
- **시나리오**: 설계상 /auth/me가 매번 DB를 읽습니다. 인스턴스 수만큼 한도가 늘어나고, 다수 Google 계정을 쓰면 무료 읽기 50k·쓰기 20k를 소진할 수 있습니다.
- **보완**:
  - /auth/me를 제한 대상에 포함합니다.
  - Cloud Run 최대 인스턴스 수를 고정해 전역 상한을 계산합니다.
  - 일일 신청 생성 총량에 상한을 둡니다.
- **인수 테스트**: 한도를 초과하면 429를 반환하고, 쓰기 횟수가 늘지 않아야 합니다.

**[P2] 현재 확장이 403 사유를 버림**
- **위치**: authWorker.entry.js:85-88
- **문제**: 403 응답의 `detail.message`를 무시합니다. 그래서 auth.py:218(Google·이메일 인증 실패)과 :223(허용목록 미포함)을 구분할 수 없습니다.
- **보완**:
  - 설계에서는 /auth/me 응답에 `access_status`와 오류 `code`를 계약으로 고정합니다.
  - 현재 코드에서는 code와 message를 함께 표시합니다. 토큰은 표시하지 않습니다.

**[P2] 모드·저장소 조합 검증**
- **위치**: docs:106, docs:22
- **내용**: 원칙은 설계에 이미 있습니다. 여기에 "Firestore 저장소이면서 mode≠firebase"이거나 `SIDE_B_ADMIN_UIDS`가 비어 있으면 서버 기동을 실패시키는 구현 규칙을 추가할 것을 권합니다.
- **인수 테스트**: 해당 조합으로 기동하면 실패해야 합니다.

## 3) 타당한 설계

- **인증 단계**: 신원 검증 경로는 기존 auth.py:198-218을 유지합니다. 여기서 승인 검사(:219-223)를 분리합니다.
- **/auth/me**: 신원이 유효하면 200을 반환하고 `access_status`와 `can_manage_access`를 담습니다.
- **기능 API**: `require_approved` 의존성에서 문서를 읽어 approved일 때만 통과시킵니다. 장애 시 503을 반환합니다.
- **관리 API**: `require_admin`이 토큰 UID를 서버 목록과 대조합니다.
- **확장**: 403에서 signOut하는 처리(:203-208)는 계정 거부 코드일 때만 수행합니다.

이 구조는 설계 9·43·49줄과 일치합니다.

## 4) 배포 전 체크리스트

1. 운영 Firebase UID 확인 및 `SIDE_B_ADMIN_UIDS` 설정
2. 기존 허용목록을 UID 기준 approved로 이관
3. Firestore 규칙 deny-all, 서비스 계정 IAM 최소화
4. 전체 리비전·태그 목록 확인 후 구 태그 제거
5. 운영 `SIDE_B_AUTH_MODE=firebase`, 공유 토큰 환경변수 제거
6. 신 확장 배포 후 관리자·pending·차단 계정으로 실제 Google 로그인 E2E 수행. 현재 테스트 173개에는 E2E가 포함되어 있지 않습니다.
7. 미리듣기 Blob 경로와 차단 시 403 확인
8. 롤백 리비전도 Firestore 정책을 쓰는지 확인

## 5) 현재 승인 거절 원인: 입증 가능한 범위

**입증 가능한 것**
- 오류 문구가 "승인되지 않은 계정"이면 `/auth/me`가 정확히 403을 반환한 것입니다(authWorker.entry.js:86).
- 현재 서버 코드에서 /auth/me의 403은 `AuthenticationDeniedError`에서만 나옵니다(routers/auth.py:43-47).
- 토큰 무효는 401, 검증 불가는 503으로 분리됩니다. 따라서 403이었다면 서명·프로젝트·만료·취소 검사는 통과한 것입니다. 이는 화면에 표시된 서버가 이 코드를 실행 중이라는 전제에서 성립합니다.
- 그렇다면 원인은 auth.py:213-218(Google 제공자 또는 email_verified 실패)이나 :219-223(UID·이메일 허용목록 미포함) 중 하나입니다.

**미확인인 것**
- 두 원인 중 어느 쪽인지는 확장이 사유를 버리기 때문에 판별할 수 없습니다.
- 새 리비전의 `FIREBASE_ALLOWED_*` 값과 파싱 방식(설정 로더 코드는 제공되지 않음)도 확인되지 않았습니다.
- 다음 중 하나로 확정해야 합니다.
  - 403 응답 본문의 `detail.message`
  - Cloud Run 로그
  - `gcloud run services describe`로 조회한 환경변수

**판단 근거로 삼을 수 없는 것**
- 403 화면에 표시되는 이메일은 서버가 판정한 값이 아니라 클라이언트 Firebase의 `user.email`입니다(authWorker.entry.js:87).

## Codex 근거 재확인 메모

- 호출 응답 model=claude-opus-5-5, status=completed를 outputs/auth-review/claude-opus-5-5-review-response.json에 저장했다. Claude Code는 요구 버전을 충족하도록 2.1.118에서 2.1.289로 업데이트했다.
- 태그 URL이 트래픽 비율과 무관하게 지정 리비전에 직접 연결된다는 특성은 Google 공식 문서로 확인했다: https://docs.cloud.google.com/sdk/gcloud/reference/run/services/update-traffic . 현재 운영 태그/리비전 전체 목록과 차단 계정의 기능 호출은 미검증이다. 따라서 리뷰의 우회 시나리오는 배포 전 차단해야 하는 위험이며, 실제 침해가 입증된 것은 아니다. 옛 서비스의 일반 URL 및 다른 공개 별칭도 검사 대상에 포함한다.
- /auth/me에 FeatureRateLimiter 호출이 없고 FeatureRateLimiter가 인스턴스 로컬이라는 사실은 코드와 일치한다. 리뷰의 비용 소진은 가능 시나리오이며 실제 사용량 추정치가 아니다. 최대 인스턴스 수만으로 하루 요청량/비용 상한을 보장할 수 없으므로 UID별 제한과 전체 신청/조회 예산을 별도로 정한다.
- 감사 작업 ID는 요청자 UID와 함께 멱등성 범위를 정하고, 이전 성공 재사용 전에 현재 요청자의 관리자 권한을 다시 확인해야 한다. 현재 설계의 '호출마다 확인' 원칙을 유지한다.
- 리뷰 3절의 '403에서 signOut은 계정 거부 코드일 때만'이라는 문장은 구체화가 필요하다. 제안한 승인 설계에서는 pending/rejected/blocked가 신원 인증 실패가 아니므로 Firebase 세션을 유지하고 기능만 차단한다. 토큰 무효/취소 등 신원 인증 실패와 명시적인 로그아웃을 별도 처리한다. 기존 설계의 이 원칙을 바꾸지 않는다.
- 현재 UI의 403은 Google 제공자/email_verified 검사 실패와 허용목록 미포함 모두를 같은 문구로 처리한다. 따라서 기존 대화에서 '허용목록 미일치'로만 해석한 설명은 충분하지 않았다. 현재 운영 오류 원인은 detail.message 또는 운영 리비전 설정으로 확인해야 한다.
- UID에 임의 ASCII 전용 정규식을 적용하지 않는다. 토큰의 신원 UID와 관리자 대상 UID를 문서 ID API로 다루고, 길이/슬래시 등 경로 안전성 조건을 SDK 계약에 맞춰 검증한다.

이 검토는 구현/설계 리뷰이며 운영 로그인 성공 또는 관리자 승인 기능의 보안 테스트 완료를 의미하지 않는다. 서버/DB/권한 정책은 변경하지 않았다.
